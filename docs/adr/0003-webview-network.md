# ADR 0003: The webview's network: a dead proxy everywhere, macOS 14, and what is disclosed

- **Status:** Accepted
- **Date:** 2026-10-03
- **Decider:** João Vitor Pina

## Context

Spike S2.7 asks whether any process of Navaja's tree sends a packet off the machine, idle or in use. Its PASS is "a VM NIC capture shows no packets from the process tree, idle or in use". Its fallback is "browser args or policies; anything left over is disclosed verbatim in privacy.md". [spikes.md](../spikes.md) S2.7 has the method and every run.

The run of record before this decision, [37156112676](https://github.com/joaovitorpina/Navaja/actions/runs/37156112676) on `0866f1a`, failed on Windows and macOS. Linux passed: its webview already sent its web traffic to a dead proxy. [37158337262](https://github.com/joaovitorpina/Navaja/actions/runs/37158337262), on `90bbf7f`, found the same.

- **Windows, from WebView2's own processes:**
  - its network service reached `config.edge.skype.com` and `edge.microsoft.com`, with its own DNS queries, and looked up `wpad` through the Windows DNS client;
  - its component updater had BITS download 8 files from `msedge.b.tlu.dl.delivery.mp.microsoft.com`, 4.7 MB in all;
  - in use, it looked up the egress canary's navigation host before the guard denied the navigation.
- **macOS, from WebKit:** in use, WebKit looked up the same canary host through `mDNSResponder`.
- **Outside the tree, woken by the webview:**
  - macOS: `webprivacyd` started with the app and fetched from `wps.apple.com`, and `trustd` checked that server's certificate with `ocsp2.apple.com` for it;
  - macOS: the system's Safe Browsing service talked to Apple in each run checked; it started 4 s after the app in one of them ([37151706483](https://github.com/joaovitorpina/Navaja/actions/runs/37151706483)), but the VM also starts it by itself;
  - Windows: Windows' Microsoft-account sign-in service (`wlidsvc`) reached `login.live.com` within seconds of the app's first start, in every run checked. No log names it as acting for the app.

## Decision

### 1. A dead proxy on every OS

Outside dev mode, the webview's web traffic goes to `http://127.0.0.1:9`, a closed loopback port (`DEAD_PROXY` in `app/src-tauri/src/window.rs`). An engine hands a proxied request's host name to the proxy instead of resolving it, so nothing is looked up, and while nothing listens there, nothing leaves the machine.

- **Linux:** as before, wry sets it on WebKitGTK's `WebsiteDataManager`.
- **Windows:** WebView2's `--proxy-server`, which Microsoft's list of [WebView2 browser flags](https://learn.microsoft.com/en-us/microsoft-edge/webview2/concepts/webview-features-flags) describes as a proxy that overrides the system's settings, for HTTP and HTTPS.
- **macOS:** Tauri's `macos-proxy` feature (wry's `mac-proxy`) sets [`WKWebsiteDataStore.proxyConfigurations`](https://developer.apple.com/documentation/webkit/wkwebsitedatastore/proxyconfigurations-cdc1) to an HTTP CONNECT proxy.

The app's own pages and IPC never reach the proxy: custom schemes on Linux and macOS, and `http://tauri.localhost` and `http://ipc.localhost` on Windows, which wry serves from the app. The end-to-end suite passes with the proxy on all three OSes.

**The limit: who can listen on port 9.** The port is privileged only on Linux, while `net.ipv4.ip_unprivileged_port_start` keeps its default of 1024.
- On Windows there are no privileged ports: any local process, another user's included, can listen on `127.0.0.1:9`.
- On macOS, from 10.14 on, any user can listen on the wildcard address, `0.0.0.0:9`, and that listener also receives connections to `127.0.0.1:9`. XNU's `in_pcbbind` checks the reserved ports only for a specific address.
- Such a listener would receive what the engines send the proxy, each request's host name included, and could pass it on. That is WebView2's requests to its own services, and in use the connections that S2.7 saw stop at the proxy on every OS. TLS still protects what goes through a CONNECT tunnel.
- S2.7 cannot see this: nothing listens on port 9 on the runners, and it counts the tree's loopback connections as never leaving the machine.
- So section 4 discloses it. A port that Navaja holds itself, bound but never listening, would close the gap. On macOS, though, such a port drops connections instead of refusing them: XNU's `tcp_input` drops a segment for a socket in the CLOSED state, with no reset. So it would need its own check that the engine still gives up at once. That is not done.

### 2. macOS 14 or later

`proxyConfigurations` is a macOS 14 API, and wry's `mac-proxy` links `nw_proxy_config_create_http_connect` from Network.framework, which macOS 14 introduced. The maintainer decided that Navaja requires macOS 14 or later, rather than ship macOS without the proxy.

- `tauri.conf.json` sets `bundle.macOS.minimumSystemVersion` to `"14.0"`. Tauri's bundler writes it to the bundle's `Info.plist` as `LSMinimumSystemVersion`, as its config reference says (tauri-utils 2.10.1). No CI job builds a bundle yet (`ci.yml` and `spikes.yml` build with `--no-bundle`), so that rests on Tauri's documentation until `bundle.yml` checks the `Info.plist` (roadmap M2b, item 4). What CI does show: tauri-build 2.7.1 passes the setting on as `MACOSX_DEPLOYMENT_TARGET` outside dev (`src/lib.rs`, lines 780 to 783), and the built files declare 14.0 (below).
- `.cargo/config.toml` sets `MACOSX_DEPLOYMENT_TARGET` to `14.0` for every cargo build. In a `tauri build`, tauri-build sets it from the bundle setting, but only for the app's own crate; its dependencies, clippy, nextest and dev builds would use rustc's defaults, 11.0 on arm64 and 10.12 on Intel.
- `scripts/check-macos-target.sh` reads the version back from what each macOS build in CI produced, and refuses a `minimumSystemVersion` below 14.0. In ci.yml it covers clippy's build scripts and proc macros, nextest's test binaries, the Intel step's C objects and the app; in spikes.yml, the app S2.7 runs.
- macOS caches in CI are keyed apart. Cargo rebuilds a cached crate for a new deployment target only if the crate reads it, so main's cache kept 359 proc macros and build scripts built for 11.0 ([37160662985](https://github.com/joaovitorpina/Navaja/actions/runs/37160662985)).

### 3. Browser arguments and preferences

- **Windows: no browser arguments of Navaja's own.** wry 0.57.0 adds `--proxy-server` after its defaults, in `create_environment` of its `src/webview2/mod.rs`: `--disable-features=msWebOOUI,msPdfOOUI,msSmartScreenProtection`, then `--autoplay-policy=no-user-gesture-required` while autoplay is on, which is wry's default and Tauri keeps it. The WebView2 browser process's 4688 in [37172832953](https://github.com/joaovitorpina/Navaja/actions/runs/37172832953) shows all three. With that, nothing left the process tree ([37160662987](https://github.com/joaovitorpina/Navaja/actions/runs/37160662987)). The component updater's check stopped at the proxy, so BITS had nothing to download, and nothing looked `wpad` up. So these were not needed:
  - `--disable-component-update` and `--disable-background-networking`, Chromium switches ([`chrome_switches.h`](https://github.com/chromium/chromium/blob/af1f5c41f0cb8eb44adb549f17e176cc0df1aa54/chrome/common/chrome_switches.h#L234-L245)) that Microsoft's flags list does not name.
  - Tried and dropped: turning off WebView2's single sign-on with the Windows account (`msSingleSignOnOSForPrimaryAccountIsShared`, `msSingleSignOnForInPrivateWebView2` and `msAllowAmbientAuthInPrivateWebView2`, all on Microsoft's list), to stop `wlidsvc`'s contact (section 4). With them off it still came, at +7.3 s ([37162299733](https://github.com/joaovitorpina/Navaja/actions/runs/37162299733)), so Navaja does not pass them.

  Microsoft's flags page says apps "in production shouldn't use WebView2 browser flags"; Navaja relies on one, `--proxy-server`, through wry. An argument Navaja passes later replaces all of wry's, so it must repeat all three, in one place in `window.rs` (architecture §5): `--disable-features=msWebOOUI,msPdfOOUI,msSmartScreenProtection`, `--autoplay-policy=no-user-gesture-required` and `--proxy-server=http://127.0.0.1:9`. The arguments that `a969a4b` built were missing the autoplay switch, so that run dropped it; `1fac01a` removed them.

- **macOS:** `WKPreferences.fraudulentWebsiteWarningEnabled` is off ([public API](https://developer.apple.com/documentation/webkit/wkpreferences/isfraudulentwebsitewarningenabled), macOS 10.15 and later, on by default), next to WebRTC (`platform/macos.rs`). Apple documents it as whether the web view warns about suspected fraudulent content; the webview only shows Navaja's own pages, so it needs no such warnings. The aim is that WebKit stops asking the system's Safe Browsing service about pages. **CI has not shown that it does.**
  - In every run since this change whose macOS job finished, the VM had started the service by itself before the app first ran: as the baseline began in [37162299733](https://github.com/joaovitorpina/Navaja/actions/runs/37162299733), 8.5 min before it in [37163502511](https://github.com/joaovitorpina/Navaja/actions/runs/37163502511), 38 s into it in [37164320626](https://github.com/joaovitorpina/Navaja/actions/runs/37164320626), 4 min before it in [37165352245](https://github.com/joaovitorpina/Navaja/actions/runs/37165352245), 1.5 min before it in [37167561422](https://github.com/joaovitorpina/Navaja/actions/runs/37167561422), 46 min before it in [37168559527](https://github.com/joaovitorpina/Navaja/actions/runs/37168559527), 9.4 min before it in [37169461485](https://github.com/joaovitorpina/Navaja/actions/runs/37169461485), 4 min before it in [37170350998](https://github.com/joaovitorpina/Navaja/actions/runs/37170350998), 45 s into it in [37172832953](https://github.com/joaovitorpina/Navaja/actions/runs/37172832953), and 39 min before it in [37173797683](https://github.com/joaovitorpina/Navaja/actions/runs/37173797683).
  - S2.7 counts a WebKit daemon as the app's only if it starts within 15 s after the app. It cannot tell the traffic of a daemon that was already running apart from the app's, so it left the service out, and the service's packets in the app's phases went unchecked: 35 in idle and 6 in use in 37162299733, 44 in idle in 37164320626, 39 in idle in 37165352245, 40 in idle in 37167561422, 23 in idle in 37168559527, 42 in idle in 37170350998, 37 in idle in 37172832953, 35 in idle in 37173797683, and none in 37163502511 and 37169461485.
  - Before this change, the service started 4 s after the app in one run ([37151706483](https://github.com/joaovitorpina/Navaja/actions/runs/37151706483)); no run since has shown whether the app still wakes it.

### 4. What is disclosed

The fallback's "disclosed verbatim" part: what system services that the webview wakes still send, which no setting reaches. S2.7 reports it as disclosed, in a summary row of its own, instead of failing on it; anything else, or the same traffic in another OS or phase, still fails. Nothing from the process tree itself is on the list.
- The entries are in `scripts/spikes/s2-7-disclosed.tsv`, one per (OS, phases, service, hosts). Each names only the phases its traffic was seen in.
- The service is the one the check matches: the process a packet was for.
- The purposes, here and in the TSV, are short labels. What `privacy.md` says is the text at the end of this section.

| OS | Phases | Service | Hosts | Purpose, in short |
|---|---|---|---|---|
| macOS | idle | `webprivacyd` | `wps.apple.com` | what `webprivacyd` fetches when WebKit asks it for its storage-access quirk lists |
| macOS | idle | `webprivacyd` | `ocsp2.apple.com` (CNAME `ocsp2.g.aaplimg.com`) | the certificate check of that connection, which `trustd` sends for `webprivacyd` |
| Windows | idle | `svchost.exe [wlidsvc]` | `login.live.com` | Windows' Microsoft-account sign-in |

That text also says who could listen on the dead proxy's port (section 1). S2.7 sees no traffic of that kind, so it has no entry.

How S2.7 matches a packet to an entry: the packet's service is the entry's, and every name the packet is tied to is one of the entry's hosts.

- A DNS packet is tied to the name it asks for.
- Any other packet is tied, through its connection, to the lookups that its own process made before the connection began and that gave its remote address. On macOS those are the lookups mDNSResponder made for the same process (pktap's eproc, name and PID); on Windows, the process's own lookups in the DNS client's log (event 3008).
- So a shared address counts only for what that process looked up. Apple's edge servers answer for many names: in 37164320626, `17.253.5.143` answered for `ocsp2.apple.com`, `valid.apple.com` and `updates.cdn-apple.com`, among others. Until `6ab9fc2`, any name a captured answer gave for the address counted, so the `ocsp2` entry would have covered a connection of `webprivacyd`'s to another Apple service there.
- A connection with no such lookup is tied to nothing, and fails.
- The limit: on macOS, a name looked up stands for the names whose CNAMEs lead to it, as far as the job's captures show, because mDNSResponder may ask only for a CNAME's target. That is why the `ocsp2` entry lists `ocsp2.g.aaplimg.com` too. A lookup of that name made for `webprivacyd` would count as the entry's even if some other name, whose CNAME no capture saw, had led to it.

What was tried first:

- **`webprivacyd`.** WebKit asks it for its storage-access quirk lists unconditionally, in `WebProcessPool`'s constructor ([`WebProcessPool.cpp`](https://github.com/WebKit/WebKit/blob/10740b3a1fa50537a0fbea349eb9130ac609d852/Source/WebKit/UIProcess/WebProcessPool.cpp#L345-L372), under `ENABLE(ADVANCED_PRIVACY_PROTECTIONS)`), and the request ([`WebPrivacyHelpers.mm`](https://github.com/WebKit/WebKit/blob/62300d55e70a29e7555d266eca4c8ff4d4e5cf1e/Source/WebKit/Platform/cocoa/WebPrivacyHelpers.mm#L270-L342)) checks only that the WebPrivacy framework is there. No `WKWebView`, `WKWebsiteDataStore` or `WKPreferences` setting, public or private, gates it, so there is nothing to try in the app. Whether the daemon then downloads depends on its own copy: on these fresh VMs, it did every time.
- **`trustd`** checks the certificate of `webprivacyd`'s connection; it goes with the entry above.
- **`wlidsvc`**, Windows' Microsoft-account sign-in service, reached `login.live.com` shortly after the app's first start in every Windows run: it looked the name up 1.2 to 2.3 s after WebView2's browser process started, before the proxy and with it. That was 2.3 to 6.4 s after `navaja.exe` started with the proxy, and 16.5 s in [37168559527](https://github.com/joaovitorpina/Navaja/actions/runs/37168559527), where WebView2 started 14.4 s late. WAM's account provider started next to it. No log names the app or WebView2 as asking, and the service also talks without the app:
  - in the baselines of 37154768748 (+239 s), [37160662987](https://github.com/joaovitorpina/Navaja/actions/runs/37160662987) (+124.5 s), [37162299733](https://github.com/joaovitorpina/Navaja/actions/runs/37162299733) (+206.8 s), [37164320626](https://github.com/joaovitorpina/Navaja/actions/runs/37164320626) (+203.5 s) and [37169461485](https://github.com/joaovitorpina/Navaja/actions/runs/37169461485) (+148.5 s). In the last four the service started by itself and looked `login.live.com` up 0.1 to 0.2 s later. In 37169461485 it was still running when the app started, and looked the name up again 1.4 s after WebView2's browser process started;
  - later in idle phases, next to Windows Update's medic service.

  wry leaves WebView2's `AllowSingleSignOnUsingOSPrimaryAccount` at its default, off ([Microsoft's reference](https://learn.microsoft.com/en-us/microsoft-edge/webview2/reference/win32/icorewebview2environmentoptions)), and turning off the single-sign-on features changed nothing (section 3). No other WebView2 option or switch is known to reach it. S2.7 counts its connections, and those of the account provider, in the 15 s after a start of `navaja.exe` or of WebView2's browser process as the app's, and discloses this one. The window opened only at `navaja.exe`'s start until `3b21796`, so in 37168559527 the contact went to the review list instead.

**The text for `privacy.md`**, word for word (roadmap M6, item 6). It is the one text `privacy.md` must carry; the table and the TSV above only point to it:

> **macOS: WebKit's fixes for particular websites.** When Navaja starts, macOS's WebKit asks the system service `webprivacyd` for its storage-access quirk lists: fixes for particular websites, for how they reach their cookies across sites. The service may then fetch data from Apple (`wps.apple.com`), and macOS's `trustd` checks that server's certificate with Apple (`ocsp2.apple.com`). These are macOS services, not part of Navaja, and Navaja cannot turn them off. Other apps that use WebKit, Safari among them, ask the same service.
>
> **Windows: the Microsoft account sign-in service.** Shortly after Navaja starts, Windows' Microsoft account sign-in service (`wlidsvc`) can contact Microsoft's sign-in server, `login.live.com`. In our tests it did so at the first start of Navaja in each session. Windows also runs this service when Navaja is not running, and no Windows log names Navaja or its webview (Microsoft Edge WebView2) as the cause. It is part of Windows, and Navaja cannot turn it off. Navaja itself signs in to nothing.
>
> **Windows and macOS: who could listen where Navaja's web requests end.** Navaja sends its webview's web requests to a closed port on your own computer (`127.0.0.1`, port 9), so that they go nowhere. On Windows any program on the computer, and on macOS a program of any user, could open that port. It would then receive those requests, with the names of the servers they were meant for, and could pass them on. Navaja does not check whether something listens there. On Linux only an administrator can open that port.

## Consequences

- Navaja requires macOS 14 or later. Its binaries declare 14.0, which CI checks, and wry links a function that macOS 14 introduced; no CI job runs it on macOS 13. The bundle's `LSMinimumSystemVersion`, which macOS reads before it opens an app, should say 14.0 too; `bundle.yml` checks that when it lands (roadmap M2b, item 4).
- Navaja passes WebView2 no arguments of its own. One added later replaces all of wry's, so it must repeat wry's defaults and `--proxy-server`. The defaults are the `--disable-features` list and, while autoplay is on, `--autoplay-policy=no-user-gesture-required` (`create_environment` in `src/webview2/mod.rs`). A wry or Tauri upgrade must check them again against that function.
- On Windows and macOS another local process can take the dead proxy's port (section 1). A port that Navaja holds itself would close that; it is not done.
- Microsoft may change or remove WebView2's browser flags, `--proxy-server` included. S2.7 runs again in M6 (roadmap, item 7), and `spikes.yml` can be run by hand after a WebView2 or macOS update.
- `privacy.md` (roadmap M6, item 6) carries the text for it in section 4 word for word. The table there and `scripts/spikes/s2-7-disclosed.tsv` are the check's labels, not that text. A new entry needs a run that shows the traffic, an attempt to stop it, and a change to this ADR and its text.
